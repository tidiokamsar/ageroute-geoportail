## E. Écarts de contrat constatés (backend non modifié)

1. **E1, bénéficiaire gestionnaire sans liste (reste de C1B-O2).** `GET /:id/export/derogations` est réservé à l'ADMIN (`projets-voirie.dossier-technique.routes.ts`, garde `administrateur`) et aucune route ne rend « les dérogations qui me visent ». Un GESTIONNAIRE bénéficiaire ne peut donc pas **voir** qu'une dérogation lui est accordée : l'interface lui permet de l'utiliser par son identifiant, que l'ADMIN lit dans la liste et lui communique hors de l'application (aucun envoi de message par l'application : décision 2, section 9). À trancher : une route `GET /:id/export/derogations/miennes` (ou un filtre `?beneficiaire=moi` ouvert aux décideurs) rendant les dérogations du compte. L'interface est prête à la lire (`derogationsUtilisables`).
2. **E2, empreinte calculée dans le navigateur.** Le mandat la demandait « si le contrat le prévoit ainsi » : le contrat D1 (sections 2.1 et 5) prévoit l'inverse, le fichier part en multipart et le serveur en calcule l'empreinte et le format par le contenu, puis l'oublie. L'interface suit le contrat ; elle ne lit pas le fichier (le test statique du module interdit `FileReader` et `.arrayBuffer(` dans le module). Calculer l'empreinte localement (SubtleCrypto) pour l'afficher avant l'envoi demanderait de lire le fichier : non fait.
3. **E3, choix du bénéficiaire.** Le contrat X1 ne fournit pas de liste des comptes habilités : l'interface lit `GET /users` (route ADMIN hors module, déjà utilisée par le workflow pour les référents), sans filtre de périmètre ; le périmètre est vérifié par le serveur à l'octroi (422 `BENEFICIAIRE_HORS_PERIMETRE`, expliqué). Au-delà de 200 comptes par rôle, la liste est incomplète (non signalé par le serveur, `total` seulement).
4. **E4, `API.md` X1, tableau des routes.** La ligne `POST /:id/export/derogations` dit encore `beneficiaireId?` et l'état `DISPONIBLE|UTILISEE|EXPIREE` ; le code et la section des corrections disent `beneficiaireId` obligatoire et l'état `RESERVEE` en plus. L'interface suit le code (bénéficiaire obligatoire, quatre états).
5. **E5, libellés de la complétude sans accents.** `completude.noyau.ts` rend des libellés ASCII (« Recolement d'un reseau deplace ») : l'interface affiche ses propres libellés accentués pour les codes connus du contrat, et le libellé du serveur pour un code inconnu.
6. **E6, `piecesManquantes` non bornée.** La complétude ne tronque que la lecture des documents (`documents.tronque`) ; la liste des pièces manquantes n'a pas de plafond côté serveur. L'interface en montre 20 puis les autres à la demande.
7. **E7, statut `REMPLACE` dans les versions courantes.** Après le retrait d'une version, la précédente reste `REMPLACE` et apparaît parmi les versions courantes (revue D1, M1) : le bouton « Nouvelle version » y est proposé, comme le contrat l'indique ; en vue « toutes les versions », une version qui n'est pas la dernière reçoit 409 `VERSION_NON_COURANTE`, expliqué.
8. **E8, attente bornée côté navigateur.** Le contrat fixe 50 s au plus côté serveur et nginx coupe à 60 s ; l'interface abandonne à 70 s. Si le DSI baisse `proxy_read_timeout`, la valeur de l'interface reste au-dessus (sans effet nuisible : nginx coupe avant).
